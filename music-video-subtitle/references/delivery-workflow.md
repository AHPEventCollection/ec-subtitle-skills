# 样式、压制与交付

## 标准样式与预览

```powershell
python -B $pipeline style --mv-dir $mvDir
python -B $pipeline preview --mv-dir $mvDir
```

`style`从当前审定字幕派生标准ASS：

- 中文在上，暖黄色，80号
- 日文在下，白色，57号
- `WrapStyle:2`，不自动折行
- 超宽行保持字号，只降低`\fscx`；所需水平缩放低于55%时失败并退回人工调整
- 分辨率与画布按片源宽高比适配

颜色、字号和处理顺序直接采用本项目规范，不读取旧成品猜测参数。完整质量门禁见[quality-gates.md](quality-gates.md)

MV预览不切片。候选复对和正式预览共用唯一的`review/preview/`目录及其中的完整片源，不按次数新增目录，不复制视频，不删除用户放入的其他文件；只更新字幕与检查点。正式预览在片源旁放同名外挂ASS，并把`preview.md`和`preview-windows.tsv`放在同一目录；不重新编码视频，不把字幕封装进MKV。时间窗口覆盖字幕开头、中段、结尾、最长行、亮场、暗场和末句消失位置。候选复对、正式预览和成品抽帧中的人类可见检查点统一使用`MM:SS.mmm`，超过一小时使用`HH:MM:SS.mmm`，不得输出裸秒数；内部计算和FFmpeg定位仍使用精确秒数。画面含原生歌词时，预览必须同时检查双语字幕与画面歌词是否逐句对应；只确认样式清晰不能代替时间轴核对

确认时间轴或样式有问题时直接修改`subtitle/master.ass`，再运行`style`和`preview`；style保留人工样式与逐事件标签，仅按片源适配画布。不再建立SRT主文件，旧项目SRT仅作一次性转换输入且不自动删除

单独运行`preview`表示用户要先看正式样式，生成后必须停下交付检查。若用户已经看过候选预览并明确选择当前候选，同时明确说“出片”“直接压正片”或同义表达，这一决定同时授权建立`master.ass`、生成正式ASS预览、执行自动门禁、压制和机器验收；正式预览仍必须生成，但不再插入第二次人工确认。只有自动门禁发现真实异常、输入已变或用户明确要求先看样式时才暂停

脚本只用文件修改时间检查直接依赖：`master.ass`更新后旧样式ASS不能预览，ASS或片源更新后旧预览不能压制。这不是持久化状态，也不生成哈希清单

## 递增版本压制与验收

```powershell
python -B $pipeline finish --mv-dir $mvDir --candidate "<已确认候选.srt>"

# 已有人工审定master.ass时
python -B $pipeline finish --mv-dir $mvDir

# 只调试单步时使用
python -B $pipeline render --mv-dir $mvDir
python -B $pipeline validate --mv-dir $mvDir
```

用户确认候选并明确要求出片时优先运行`finish`。它按顺序执行`build-subtitle`（仅首次需要）、`style`、`preview`、`render`和`validate`，任一步失败都会在压制前或验收处停止，不靠批准令牌或状态文件。已有`master.ass`时不允许再次传入候选

如果`work/publish-copy.md`和封面素材在验收后已就绪，`finish`在机器验收后自动运行交付素材落盘，生成同版本文案与封面。无论素材是否齐全，`finish`最后返回`output/delivery-status.vNN.md`，明确列出MP4、ASS、四平台文案、封面、机器检查和人工检查；其中任何一项未完成时不得向用户报告完整交付

`render`要求已有且未过期的预览，生成`<mv-id>.hardsub.vNN.mp4`和`<mv-id>.subtitle.vNN.ass`。视频重编码，音频必须直拷贝；源音频不兼容MP4直拷贝时失败，不偷换转码

`validate`完成全片音视频解码、尺寸和时长核对、源与成品音轨内容校验，并从当前成品抽取典型画面。它生成机器检查和未勾选的人工检查表。机器通过不等于人工通过，必须播放关键段并查看抽帧后逐项勾选

正式预览时间窗口和成品抽帧均由脚本生成，不再另外手写FFmpeg截图命令。片源复用后不追加整份视频的通用SHA256比对；通用文件哈希、批准令牌和工作流状态文件都不产生。这里只保留音轨内容校验，因为它直接证明音频直拷贝没有改变

## 发布文案

用已确认的官方资料完成标题、背景、来源和话题，字段结构按[MV文案格式](publish-copy-format.md)准备；固定标题前缀、正文段落和是否重复标题读取当前项目的本地约定。用户修改后的正式MD、明确的平台差异、相同正文要求和实际话题选择优先，不得用旧草稿覆盖

话题执行[话题选择与核验](publish-copy-format.md#话题选择与核验)，项目专属禁用词、查询类别和作品名称格式按本地规则，保留实际查到的名称与关联信息，不照搬旧任务话题

- 微博：本平台标题、正文、歌词来源和双井号话题
- 小红书：本平台标题、正文、歌词来源和单井号话题
- B站：本平台标题、正文、歌词来源、独立原视频字段及顿号分隔标签
- 视频号：短标题、紧凑正文、来源和话题

默认四个平台定稿先保存为：

- `work/publish-copy.md`

用户要求保留原文歌名时，将已核实歌名写入`work/publish-title.txt`（单行）。交付和发布预检会验证各平台标题包含该原文，小红书标题最多20字；超长时缩短栏目或艺人前缀，不擅自翻译歌名。`标题：`后空行直接接正文也能正确解析

默认必须直接使用`## 微博`、`## 小红书`、`## B站`、`## 视频号`四个二级标题。用户明确排除平台时，在本支工作区的`work/publish-platforms.txt`中每行写一个实际交付平台，只允许`微博`、`小红书`、`B站`、`视频号`，文案只需包含声明的平台，不得生成被排除平台的占位内容。不要在文案文件前面堆研究记录、多个版本草稿或“公开后再补”清单。`finish`或`stage-delivery`验证后复制为与视频同版本的正式文件：

- `output/<mv-id>.publish-copy.vNN.md`

每个章节独立适配对应平台

每个实际交付平台章节都必须原样带上`subtitle/chinese-source.txt`中的一行来源，不能只在合并文件开头统一写一次，因为各平台文案会被分别复制发布：

- 中文主体来自网易云，模型仅校对或少量补译、改译：`中文歌词来源：网易云音乐`
- 中文主体由模型翻译且采用网易云中文：`中文歌词来源：网易云音乐、翻译模型（<实际模型名>）`
- 中文主体由模型翻译且未采用网易云中文：`中文歌词来源：翻译模型（<实际模型名>）`

公开署名先按[MV文案格式](publish-copy-format.md)核定并同步来源文件，不能因候选脚本自动记为混合来源就保留不适用的模型署名

每个平台正文另含制作署名四项，使用模型、Token用量及口径、制作耗时、`使用技能：ec-subtitle-skills`；歌词来源中的翻译模型与实际参与制作的模型分别核定。微博、B站、小红书各附独立章节评论，B站简介不包含章节表，至少准备开场与结束段真实起点。发布前预检检查字段与章节文字，原生章节保存仍需按项目流程回读

未核实的信息不写，文件不得为空或保留占位词。发布动作仍需用户明确授权

用户已修改`output/<mv-id>.publish-copy.vNN.md`时，该文件是本期文案真相源，`work/publish-copy.md`只作旧草稿，不自动回灌、补回用户删掉的段落或统一平台差异。系列内容按用户要求引用同系列的上一篇：B站使用已核验BV号或B站地址，小红书使用站内笔记引用，不粘贴外部URL；不能把全账号最新一条误当作上一篇

## 浏览器发布待提交

只有用户要求上传或准备发布页时才执行，完整操作合同见[发布待提交与故障止损](publish-handoff.md)。先运行`scripts/publish_preflight.py --mv-dir <工作区>`，只读检查正式MD、媒体和各平台字段；缺少上一篇时只阻止该平台的待提交完成判定，不阻止其他平台准备。该脚本不打开浏览器、不上传、不修改文案

不得临场并发填写同一浏览器内的字段，不使用无名称textbox或未限定的first()猜测正文编辑器。先在一个确定的可见字段验证输入在失焦和重渲染后仍保留，再复用成功输入方式。已知会回退的fill不再重试；字段失败后最多一次有不同机制的修复，同一连接恢复最多一次。没有真正完成所有字段、封面和上传回读，不得说待提交就绪

## 封面图

YouTube来源默认使用本支视频自己的缩略图，优先复用source/source.webp等已下载原图，保持尺寸、构图与比例转为work/cover-source.jpg；缺失时只补取同视频高清缩略图，不搜索歌曲封面、不从MV截图。其他来源采用歌曲对应的正式发行图，具体顺序见[封面来源](cover-sources.md)

finish在正片编码和机器验收期间自动准备封面。工具返回运行中会话后，利用压制时间完成work/publish-copy.md，使用同级临时文件完整写入后原子替换，避免读到半稿；不调用额外模型。验收后再次检查文案章节、署名和封面，齐全就落盘，未齐全则返回真实缺项，不把素材缺失当作视频压制失败

晚于压制就绪的素材单独运行stage-delivery补齐，不重新压制。指定已经核实的定稿文案或封面使用--publish-copy和--cover。同版本封面只有用户明确要求修改时加--replace-cover，仅替换同格式封面；已有正式文案不同则拒绝覆盖，优先传入用户修改后的正式MD。命令不执行发布

默认交付一张保持原比例的封面，最短边至少720px，不放大低清图片；原素材保持不变。项目要求额外比例或多版时，按本地规格另行制作并检查主体、文字、尺寸与构图。不适合裁切时报告对应规格待调整，不强裁或拉伸。取图失败时保留正片并报告缺项，不用其他图片补位

CLI生成output/<mv-id>.cover.vNN.jpg或.png并检查单张原比例封面，具体见[封面来源](cover-sources.md)。项目额外要求的版本须另行回读，不能用CLI通过代替本地扩展规格的验收

## 交付检查与归档

先读取当前项目AGENTS.md中的本地归档约定及其指定的权威规则，确定内容分类、归档根目录、文件夹命名及保留范围，再构造`--destination`。已有固定位置必须沿用，不能把下面的路径占位符理解为可以自行新建archive或归档根目录。多曲Live按实际内容分类，不因使用MV工具就按单曲MV归档；未完成实验不得冒充完成作品

保存成品、正式字幕、定稿文案、封面、人工修改及必要工程和来源记录；唯一源文件与必要材料必须先保存并核验，工作区外的原始素材不随归档移动。具体长期保留范围和归档布局按本地约定执行，复制完整工作区不代表冗余媒体必须全部长期保留；整理前核对唯一内容和已经验证的副本

```powershell
python -B $pipeline delivery-check --mv-dir $mvDir
python -B $pipeline archive --mv-dir $mvDir --destination "<archive-directory>"
```

`delivery-status`随时回读同版本MP4、ASS、四平台合并文案、唯一封面、机器检查和人工检查，缺一项就明确标记交付未完成。机器报告必须包含本版本成品路径和全部四项通过结果，人工表必须包含本版本标题及七项明确勾选；空表、缺项、重复、未通过或检查后MP4／ASS已更新均列出具体原因。人工检查由用户实际完成后运行`delivery-check`，它使用相同规则再次确认所有项目并生成`output/delivery-check.vNN.md`。旧人工记录保持原样，修改成品或ASS后需重新检查确认，脚本不自动补勾

归档和工作目录清理按项目规则或本次用户指令的明确范围执行，已有清理授权直接沿用；未包含清理时完成复制与核验后保留工作区。归档不等于作品验收通过，未完成的播放检查、封面或平台提交如实保留，不得为了归档补勾验收

`archive`将正式`output/`放入目标根目录，将源素材、字幕、人工修改及全部其他工程文件保存在目标`工程/`下，然后逐文件核对SHA256。目标必须在工作区外且不存在；不覆盖已有归档。复制失败保留源目录及部分归档，不得清理源目录。已有归档或清理前用同一命令加`--verify-only`只读重核，不依赖上一次的成功记录

仅当项目规则或本次指令已授权清理，且归档核验通过后，确认`$mvDir`的真实绝对路径、任务归属、保留项和链接目标，再使用宿主允许的文件删除工具清理该任务目录。Windows可单独运行`Remove-Item -LiteralPath '<已核验的本任务绝对路径>' -Recurse -ErrorAction Stop`，不默认添加`-Force`。不清理父目录、其他MV或工作区外附件；随后回读原目录已移除、归档可读、其他任务仍在，才报告清理完成

清理失败时保留已核验归档并记录实际错误，区分已完成的归档核验与尚未完成的清理。工具策略拒绝按宿主规则处理，不通过更换执行入口或修改安全配置绕过

## 交付内容

- 递增版本硬字幕MP4
- 与成品版本一致的ASS
- 包含默认四个平台或`work/publish-platforms.txt`明确声明平台的合并文案
- `subtitle/chinese-source.txt`记录的中文歌词来源，且每个实际交付平台章节各自包含相同署名
- 各平台正文的制作署名四项，以及微博、B站、小红书的独立章节评论和发布章节提醒
- 本支YouTube视频缩略图或其他来源正式发行图，尺寸与构图检查通过；额外比例和版本按项目要求交付
- 机器检查、人工检查与交付检查
- 本地保留的来源、歌词、审定字幕和预览材料


## 编码实验与直接回读

默认保持`libx264 --preset medium --crf 18`。用户明确要求硬件编码试验时，在隔离工作区运行：

```powershell
python -B $pipeline finish --mv-dir $mvDir --encoder h264_nvenc --nvenc-cq 18
# 同体积目标对照时指定视频平均目标码率，0表示纯质量模式
python -B $pipeline finish --mv-dir $mvDir --encoder h264_nvenc --nvenc-cq 18 --nvenc-bitrate-kbps <视频码率>
```

NVENC固定p7、HQ、VBR、双遍、空间与时间AQ、32帧前瞻和3个B帧，保留原有字幕滤镜、画幅、像素格式和音频直拷贝。CQ与x264的CRF不能按相同数字视为相同画质。编码器不可用时直接报错，不自动降级、换编码器或安装驱动；默认流程不受影响

`finish`在同一调用里输出各阶段进度、成品编码/尺寸/时长/大小、机器校验结论与抽帧路径，并生成同版本耗时Markdown。运行后集中读取机器报告、交付状态和抽帧，不再新增逐曲计时脚本、重复媒体探测或整份复制文件哈希；实际画面与播放检查仍需执行
